## Project

Backend (v2) for **Root Over Education**. The frontend lives next door in `../rootover-frontend-v2` and currently runs on a localStorage mock; this API replaces that mock. **`../rootover-frontend-v2/docs/BACKEND_SPEC.md` is the contract**: endpoints, response shapes (section 11), validation messages (section 9), activity-log wording (section 12) and business rules. When the spec and the mock disagree, follow the spec. Deliberate deviations from the spec:

- `User.tokenVersion` (not in the spec) is embedded in every token and incremented on password change, which revokes older tokens.
- Changing the password through `PATCH /api/me` also requires `currentPassword`, and the response then carries a fresh `token`.
- Rate-limited requests return 429 with code `TOO_MANY_REQUESTS` (not in the spec's table).
- **Email verification on sign-up** (not in the spec): `register` returns 201 `{ message, email, resendAvailableIn }` and **no token**; the token comes from `verify-email`. Login before verifying is 403 with code `EMAIL_NOT_VERIFIED`.
- **Forgot password** (not in the spec): `forgot-password` + `reset-password` with an emailed code.
- **Storage is Cloudinary only** (no local-disk fallback; tests use an in-memory driver). Application documents are stored as `{ uploadId, url, publicId, name, type, size }` taken from the `Upload` record, and the application body must send each document's upload `id`. `GET /api/uploads/private/:id` answers JSON `{ url, name, type, expiresAt }` with a 10-minute signed link (a browser `<img>`/link can't send our Bearer token, so it can't be a redirect). Upload responses also carry `id`. An avatar must be a preset (`AVATAR_PRESETS`, served in `GET /api/config` as `avatarPresets`) or the user's own upload; a course thumbnail must be the teacher's own upload.
- `VideoReportEvent.actorName` exists (the spec's schema omits it; the frontend timeline needs it).
- **Saving a `pending`, `approved` or `suspended` course runs the full submit validation** (spec: only a title is needed to save). Saving still never changes the status, but a live or under-review course can't be saved with a missing lesson or a broken video link. Drafts and rejected courses save with just a title.
- Course saves always reject non-https `noteLink` / `thumbnail` values (the spec checks the note link only on submit), because they end up in `href`/`src`.
- `CourseDetail.enrollment` (course details and the player) also carries `completedLessonIds` (only lessons that still exist), for the player's checkmarks.
- **Payments are real bKash (sandbox) instead of simulated** (see Gotchas). Checkout and the fee answer `{ paymentId, redirectURL }` instead of the finished records; the checkout body no longer takes `method` and `pay-fee` no longer takes `payerNumber` (bKash reports the wallet). Activity-log entries say `Purchased a course (<provider label>)` / `Paid the teacher registration fee (<provider label>)`, the label being `simulated payment`, `bKash sandbox` or `bKash`. 502 errors carry code `PAYMENT_GATEWAY`.
- `GET /api/admin/overview` `counts` also carries `pendingApplications` and `pendingWithdrawals` (totals behind the ≤5 lists). Admin course and withdrawal rows include the teacher (`{ id, name, teacherCode }`); withdrawal lists also return `sums` per status.

The frontend is being switched from its mock to this API in stages (user's request, 2026-10-26); its CLAUDE.md lists what's connected. Frontend edits are fine when they're part of that connection work; otherwise leave it alone.

## Commands

- `npm run dev`: dev server on http://localhost:5000 (`tsx watch`)
- `npm run typecheck`: `tsc --noEmit` (TypeScript 7)
- `npm run lint:check` / `npm run format:fix`: Biome (tabs, double quotes; `src/generated` is excluded)
- `npm run build`: compile to `dist/` (`npm start` runs `dist/src/server.js`)
- `npm run db:generate`: regenerate the Prisma client after editing `prisma/schema.prisma`
- `npm run db:migrate -- --name <change>`: create + apply a migration (needs the direct URL)
- `npm run db:deploy` / `npm run db:status`: apply pending migrations / check status
- `npm run db:seed`: wipe every table and recreate the demo data (refuses in production without `--force`)

- `npm test`: Vitest unit tests (`tests/unit`, no database; under a second)
- `npm run test:db`: Vitest against the database in `.env` (`tests/db`); run `npm run db:seed` first

Before reporting a part as done, run typecheck, lint, `npm test` and build, and smoke-test the behaviour against the running app. The build uses `tsconfig.build.json` (excludes `tests`); `tsconfig.json` type-checks everything.

## Environment

- `GET /api/config` (public) returns `{ commissionRate, registrationFee, clearingDays, minWithdrawal, payment: { provider, sandbox } }` for the frontend to display.
- Deployment, production environment and the first admin: see `DEPLOYMENT.md`. `DEMO_MODE=true` only for local demos (refused in production); `TRUST_PROXY=1` behind a host's proxy, or the rate limiters see one client.
- Email variables: `RESEND_API_KEY`, `EMAIL_FROM`. Storage: `CLOUDINARY_*`, `STORAGE_DRIVER`.
- Payment variables: `API_PUBLIC_URL` (where bKash sends the payer back), `PAYMENT_PROVIDER` (optional override), `BKASH_BASE_URL` (`BKASH_URLS.sandbox` by default or `BKASH_URLS.live`, in `src/config/index.ts`; any other value is warned about at startup), `BKASH_USERNAME` / `BKASH_PASSWORD` / `BKASH_APP_KEY` / `BKASH_APP_SECRET`. Never print them.
- `src/config/index.ts` validates every variable at startup and exits with a list of problems. Values that still contain `replace_me` (copied from `.env.example`) are rejected, so the server will not boot until the JWT secret and Cloudinary keys are real.
- `DATABASE_URL` is Neon's **pooled** URL (used by the app); `DIRECT_URL` is the same host without `-pooler` (used by the Prisma CLI via `prisma.config.ts`, because migrations don't work through the pooler). Use `sslmode=verify-full`; `sslmode=require` triggers a `pg` deprecation warning.
- **Never print `.env` or connection strings.** Mask credentials (`sed -E 's#//[^:]+:[^@]+@#//***:***@#'`) when command output could contain them, and never overwrite `.env` without preserving values the user already filled in.
- For scripts that only need to load modules without real keys, pass dummy values inline (`JWT_ACCESS_SECRET=<32+ chars> CLOUDINARY_*=dummy`); dotenv never overrides variables that are already set.

## Auth

- Passport without sessions. `src/app/lib/passport.ts` registers two strategies: `local` (`POST /api/auth/login`, via `AuthService.verifyCredentials`) and `jwt` (`Authorization: Bearer`, HS256 with issuer `rootover-api` / audience `rootover-web`). The jwt strategy reloads the user and rejects tokens whose `v` differs from `User.tokenVersion`.
- Protect routes with `auth()` (any signed-in user) or `auth("teacher", "admin")`; read the user in controllers with `currentUser(req)`. Public routes where a token only unlocks more use `optionalAuth` (no/invalid token or a banned account continue as guests). Banned users get 403 even with a valid token.
- The token's `role` claim is informational for the client; authorization always uses the database role.
- Endpoints: `POST /api/auth/register` (201, always `student`, see verification below), `POST /api/auth/verify-email`, `POST /api/auth/resend-verification`, `POST /api/auth/forgot-password`, `POST /api/auth/reset-password`, `POST /api/auth/login` (`{ token, user }`), `POST /api/auth/logout` (204, stateless), `GET /api/auth/me` (`{ user, teacher }`). Every `/api/auth` endpoint that takes credentials or codes shares `authLimiter` (20 / 15 min / IP); smoke tests that need more requests must be split across processes.
- Unknown emails are compared against a dummy bcrypt hash so failed logins take the same time; keep the same message for wrong password and unknown email.
- Sign-up and reset use 6-digit email codes (`auth.otp.ts`, table `EmailOtp`): only an HMAC is stored, 10-minute expiry, 5 wrong attempts burn the code, a new code needs a 60 s cooldown and consumes the previous one. `verify-email` → `{ token, user }`; `resend-verification` and `forgot-password` always answer the same generic 200 and do the lookup + email **in the background**, so neither the message nor the response time reveals whether an account exists (keep it that way). `reset-password` bumps `tokenVersion` (signs out all sessions) and also marks the email verified. Re-registering an *unverified* email replaces its name/password and sends a new code; a verified one is 409.
- Email goes through `src/app/lib/mailer.ts`: **Resend** (`POST https://api.resend.com/emails` with `RESEND_API_KEY`; `EMAIL_FROM` must use a domain verified in Resend). Without `RESEND_API_KEY` (allowed outside production) emails are printed to the server console as `[mail:console]`; tests capture codes from there. Seeded users are pre-verified. nodemailer/SMTP was removed (user's request, 2026-10-26).
- **Admins**: the first account to verify its email on a database with no other verified user (or admin) becomes admin (`verifyEmail`, under a `first-admin` advisory lock, so two first sign-ups can't both win). Afterwards admins manage roles with `PATCH /api/admin/users/:id/role` (`admin` for an active, verified student; `student` to remove the role); nobody changes their own role, so there is always an admin; a role change bumps `tokenVersion` (signs the account out) and is logged (`Made user an admin` / `Removed admin role`). `GET /api/admin/admins` lists them. Admins can't be banned until demoted. `npm run admin:promote` is the fallback for a lost admin.
- **Continue with Google** (not in the spec; user's request, 2026-10-26): `POST /api/auth/google { credential }` (the Google Identity Services ID token, `authLimiter`) → `{ token, user }`. `google-auth-library` checks it against `GOOGLE_CLIENT_ID` (optional; served as `googleClientId` in `GET /api/config`, `null` = off and the endpoint is 404); only `email_verified` Google emails count. A new email becomes a verified student with an unusable random password (log: `Registered a new account (Google)`; "Forgot password" sets a real one); an existing verified account just signs in (password and name untouched); an *unverified* one is verified and its password replaced + `tokenVersion` bumped (whoever chose it never proved the email). Verification by code or Google goes through `markVerified`, which holds the first-admin rule. Tests mock `google-auth-library` (`tests/db/google.db.test.ts`; `GOOGLE_CLIENT_ID` is set in `vitest.config.ts`).
- Emails are stored trimmed + lowercase (`normaliseEmail`). Responses never include `passwordHash` or `tokenVersion` (`toUserResponse`).

## Gotchas

- **Prisma 7**: generator `prisma-client` (ESM, `.js` import extensions) outputs to `src/generated/prisma` (git-ignored, rebuilt by `postinstall`). Import from `../generated/prisma/client.js`; there is no `url` in the schema's `datasource`, it comes from `prisma.config.ts`. `prisma dev` (local Prisma Postgres) hangs on `starting_up` in this environment; use Neon. A migration can be generated offline with `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script`.
- Prisma logs only warnings: handled errors (P2002 mapped to 409) would otherwise print stacks, and unhandled ones are already logged by `globalErrorHandler`.
- **Express 5**: `req.query` is a getter; `validateRequest` redefines it with `Object.defineProperty`. Rejected promises in async handlers reach the error handler without a wrapper.
- **zod 4**: use `z.url()`, `z.email()` (top-level), `error.issues`. `.min()` messages never fire for a missing field: also pass `{ error: "..." }` to the base type (`z.string({ error })`). `z.email().trim()` validates before trimming; use `z.string().trim().pipe(z.email())`.
- Scratch scripts outside the project must use the `.mts` extension, or `tsx` compiles them as CommonJS and top-level `await` fails.
- **Money** is integer BDT. `src/app/utils/pricing.ts` (quote, coupon discount, commission split, `checkCoupon`) is the only copy: the frontend has none (it reads prices/quotes from the API, the course editor's "you earn" preview from `GET /api/teacher/price-preview`, and the constants from `GET /api/config`). Derived figures live in `src/app/utils/finance.ts` (pure: `salesTotals`, `teacherFinance`, `platformSummary`, `monthlySeries`) and are loaded from the database with `finance.queries.ts` (`loadTeacherFinance(db, teacherId)`; pass the transaction client when a balance guards a write). Never compute money in services or controllers. `monthlySeries` uses Asia/Dhaka month boundaries (the frontend mock used the browser's local time). Run every multi-row write inside `prisma.$transaction`.
- **Catalog and lesson access** live in `src/app/modules/course`: `catalogWhere` (approved + teacher active) is the only definition of "in the catalog"; `courseAccess` + `toLessonPublic` are the only way to expose lessons, and they null `videoUrl` / `noteLink` for lessons the requester can't watch (spec section 7). Reuse them (and `progressOf` / `resumeLessonId`) in the player and dashboards instead of re-deriving. A non-catalog course is 404 to everyone but its owner and admins, enrolled students included (matches the frontend).
- Course lists build summaries in memory (`loadCatalogSummaries`) because price filters and sorts use derived values; sorts always end with newest + id so pages never overlap. Paginate with `src/app/utils/pagination.ts` (`{ data, pagination }`).
- **Payments go through bKash Tokenized Checkout** (user's request, 2026-10-26; sandbox for now). `src/app/lib/payment.ts` is still the only place that takes money: `paymentProvider` is `bkash` (grant token cached ~55 min, `create`, `execute` with a `payment/status` fallback) when the four `BKASH_*` credentials are set, else `simulated` (its "payment page" is our own callback with `status=success`; refused in production; tests force it via `PAYMENT_PROVIDER=simulated` in `vitest.config.ts`). The flow lives in `modules/payment`: `POST /api/checkout` and `POST /api/teacher-applications/:id/pay-fee` validate as before, create a `Payment` row (`initiated`) and answer `{ paymentId, redirectURL }`; bKash sends the browser to `GET /api/payments/<provider>/callback?paymentID&status` (public), which claims the payment (`initiated|expired -> processing`, so a refresh can't execute twice), **always confirms with `executePayment`** (the `status` parameter is never trusted for success), writes the purchase + enrollment or the fee + `under_verification` in one transaction, and 303-redirects to `<FRONTEND_URL>/payment/result?id=`. `GET /api/payments/:id` is the payer's view. Coupon uses are reserved at creation (guarded `updateMany` with `usedCount < usageLimit` field reference) and released on cancel/failure or after 30 min (`expired`, swept on the next payment start); an expired payment that bKash later confirms still completes. Paid-but-unfulfillable payments (already owned, application no longer awaiting the fee) end `failed` with a refund note and keep the `trxId`. Purchases are always `method: "bKash"`; trx ids come from bKash (`DEMO...` when simulated, `FREE...` for a 100% coupon, which skips the provider). Purchase/enrollment response shapes live in `modules/purchase/purchase.utils.ts` (reuse them for teacher earnings and admin transactions).
- The player (`/api/learn/:courseId`) reuses `CourseService.getCourse`, so it and the details page always agree on visibility and locking. Students may save any lesson they can watch (enrolled, or a catalog course's free preview), following spec 10.3 and the frontend (section 7 says enrolled only). Unsaving is idempotent (204).
- **Teacher applications** (`modules/application`): every status change goes through `transition()`, a guarded `updateMany` on the allowed from-statuses (404 if not found or not the caller's, 422 `This application can't be updated from its current status.` otherwise), so concurrent requests can't double-apply. Submissions take a per-user `pg_advisory_xact_lock` so a student never has two open applications. `approve` creates the TeacherProfile (`RO-T-26-` + serial, retried on a code clash), links it, switches the role and logs, in one transaction. The admin review endpoints (`/api/admin/teacher-applications`) live in this module, not the admin module. Identity numbers are masked with `maskIdentity` only in teacher-facing views; applicants and admins see them unmasked. Registration fees use `generateTrxId("DEMOFEE")` (simulated).
- Several routers share `/api/me`: `UserRoutes` (profile, any role), `StudentRoutes` (students only) and `ApplicationMeRoutes` (`/teacher-application`, any role).
- `/api/teachers` is the public directory (`modules/teachers`); the signed-in teacher's area is `/api/teacher` (`modules/teacher`).
- **Teacher area** (`modules/teacher`): the router requires the `teacher` role and every service starts with `teacherOf(user)` (403 without a TeacherProfile); all queries are scoped by that teacher id, so another teacher's course or coupon is a 404. `teacher.courses.ts` = course CRUD, `teacher.coupons.ts` = coupons, `teacher.service.ts` = profile/dashboard/students/earnings/withdrawals. `validateForSubmit` (pure, `teacher.utils.ts`) returns zod-style keys (`chapters.1.lessons.2.videoUrl`). Course writes lock the row (`SELECT ... FOR UPDATE`); `writeCurriculum` keeps chapter/lesson ids stable: ids of this course are updated in place (lessons may move between chapters), unknown client ids get fresh cuids, rows missing from the body are deleted (cascading their completions, saved lessons and reports), unchanged rows aren't written. Course transactions use `LONG_TX` (30 s) because Neon round trips add up. `toCourseResponse` (course module) is the owner/admin `Course` shape with raw links: never send it to students. YouTube links go through `utils/youtube.ts` (`toEmbedUrl`, the only copy; the editor checks links with `GET /api/teacher/video-link?url=`). Teacher course rows and the admin course detail carry `effectivePrice`. Withdrawals re-check `withdrawable` inside the transaction under a per-teacher advisory lock. The dashboard's `reports` counts read `VideoReport`.
- **Admin area** (`modules/admin`): the router requires the `admin` role. `admin.courses.ts` = course moderation (guarded `updateMany` on the allowed from-statuses, 404/422 like applications; approve clears `statusNote`, reject/suspend set it); `admin.service.ts` = overview, teachers, students, ban/unban (not yourself, never admins; no-op and no log when unchanged), fees, transactions (totals over the filtered set), withdrawals (pending only, guarded; the amount was reserved at request time, so approve = simulated payout, reject returns it), reports, activity logs. Per-teacher balances for lists come from `loadAllTeacherFinances` (two queries). Lists sorted "pending first" are built in memory.
- **Video reports** (`modules/report`): routes are registered by the learn (`POST /:courseId/lessons/:lessonId/reports`, `auth()` + the service's own "Only students can report videos."), student (`/me/video-reports`), teacher and admin routers. Creating reuses `CourseService.getCourse` so "can watch" matches the player (free previews included), and takes a per-student-per-lesson advisory lock for the one-active-report rule (409). Every transition goes through `transition()` (guarded `updateMany`, 404/422 like applications) and appends a `VideoReportEvent` + activity row (`<course> · <lesson>`). Boards (`board()`) accept `status` = a status, `action` (the role's to-do: teacher `fix_rejected`, `open`; admin `fix_submitted`) or `""`, plus `q` (course, lesson, reporter); they sort by that priority then newest and return `counts` over every report the role can see. Messages follow the frontend mock (e.g. reject reason: "Explain why the fix was rejected.").
- **Uploads** (`modules/upload`, `lib/storage.ts`): `storage` is Cloudinary (`STORAGE_DRIVER=cloudinary`, default) or `memory` (tests, forced in `vitest.config.ts`; refused in production). Files are typed by their first bytes (`detectMime`: JPEG, PNG, WebP, PDF), never by name; stored under a random `public_id` in `<CLOUDINARY_FOLDER>/<purpose>s`; 5 MB via multer (any multer/busboy error is a 400 on `file`); `uploadLimiter` 60 / 15 min / IP. Avatars and thumbnails are public (`secure_url`); application documents are `authenticated` assets with no public url (`private_download_url`, so it works on every Cloudinary plan). Every upload is an `Upload` row (uploader, purpose, publicId, mime, name, size); `ownPublicUpload` / `ownApplicationDoc` are the ownership checks used by `PATCH /me`, the course editor and application submit (unchanged avatars/thumbnails are accepted as they are). Approving an application copies an upload-backed photo to a public avatar when the new teacher has none (best-effort, after the transaction). Old assets aren't deleted when replaced.
- **Tests never reach real services**: `vitest.config.ts` sets `PAYMENT_PROVIDER=simulated`, `STORAGE_DRIVER=memory`, `RESEND_API_KEY=""` and `DEMO_MODE=true` for every project, so a `.env` with real bKash/Resend/Cloudinary keys is safe to test with. Keep it that way when adding services.
- DB tests (`tests/db`) start the real app with `startApp()` and get tokens with `tokenFor(userId)` (no login calls, so the auth rate limit is never hit). Tests that change seeded rows must restore them in `finally`/`afterAll`; tests that buy courses use throwaway students (see `tests/db/student.db.test.ts`) and delete them afterwards. The db project runs files one after another (`fileParallelism: false`, 120 s per test) because some tests briefly ban users or change course statuses. Neon latency occasionally times out a long test; re-run that file alone before suspecting the code. After `npm run test:db` the seed counts must be unchanged (17 users, 4 teachers, 8 applications, 5 fees, 48 purchases, 47 enrollments, 10 activity logs).
